One important rule

A successful compiler exit is not enough. Kerno must also validate the kernel format, boot header, ISO layout and emulator launch.

00
FOUNDATION5 MIN

Understand what Kerno does

Kerno has two parts. The website is the IDE you interact with. Kerno Local Service is the native companion that runs on your PC and invokes the compiler, GRUB and QEMU.

01Kerno Web IDEEditor · project · settings
↔
02Local AgentCompiler · ISO · emulator
→
03Your OSKernel ELF · bootable ISO
Key concept

The browser does not compile a kernel by itself. It sends a structured project manifest to the paired Local Agent, which runs native tools on your machine.

01
HOST SETUP15–30 MIN

Prepare your PC and connect the tools

The first supported native target is x86_64 + BIOS + GRUB + Multiboot2. You need Python 3.10+, NASM, x86_64 C/C++ compilers, an ELF linker, GRUB ISO tooling, xorriso and QEMU.

  • Python 3.10 or newer
  • NASM assembler
  • x86_64-elf-gcc and x86_64-elf-g++
  • x86_64-elf-ld, grub-mkrescue and xorriso
  • qemu-system-x86_64
Windows

Run local-agent/start-local-agent.bat. Copy the pairing token printed by the terminal into Settings → Advanced. Keep the service open while building.

02
PROJECT DESIGN5–10 MIN

Create your first kernel project

Choose New Project, then select x86_64, BIOS, GRUB, and C or C++. Keep the initial RAM and vCPU settings modest. The generated scaffold includes the Multiboot2 entry, linker script, kernel source, serial console, memory helpers and starter IDT/PMM modules.

boot/entry.asm boot/grub.cfg include/kernel/ src/kernel.cpp src/serial.cpp src/pmm.cpp src/interrupts.cpp linker.ld kerno.project.json
Why the target matters

Changing architecture metadata does not automatically convert boot assembly, ABI or linker layout. Only the x86_64 BIOS + GRUB + Multiboot2 path is currently enabled for native ISO builds.

03
BOOT ARCHITECTURE15 MIN

Understand the boot chain

On the current BIOS target, firmware loads GRUB. GRUB recognises the Multiboot2 header and transfers control to the kernel entry point. The x86_64 entry stub begins in 32-bit protected mode, checks CPU capabilities, creates an identity map for the first 1 GiB, enables PAE and long mode, switches to 64-bit code and calls kernel_main.

BIOS→GRUB→Multiboot2→32-bit entry→Long mode→kernel_main
What GRUB passes

Multiboot2 provides a boot magic value and a pointer to boot information. Kerno's entry stub forwards these values to the kernel so it can inspect the memory map and other boot tags.

04
KERNEL SOURCE20 MIN

Read the source files and linker layout

The assembly entry exports _start. The linker script places the Multiboot2 header early in the ELF image, then arranges text, read-only data, writable data and BSS at the configured kernel base. The kernel must be freestanding: no operating-system runtime or standard hosted startup is available.

  • Inspect boot/entry.asm and its handoff to 64-bit mode.
  • Inspect linker.ld and ENTRY(_start).
  • Inspect src/kernel.cpp and the serial startup messages.
  • Keep compiler ABI, entry assembly and linker architecture consistent.
Freestanding compilation

Kerno disables hosted assumptions such as built-in memory routines, stack protector, PIE and C++ exceptions/RTTI in its initial pipeline. New modules must still provide any required runtime primitives themselves.

05
LOW-LEVEL SUBSYSTEMS20–40 MIN

Understand memory, console and interrupts

The starter PMM uses the Multiboot2 memory map to manage 4 KiB physical frames in the first 1 GiB identity-mapped region. Serial output uses COM1 for diagnostics; the text console uses legacy VGA text memory. The IDT installs a fail-stop default handler.

Important limitation

This is a learning kernel foundation, not a complete OS. It does not yet implement a general heap, complete virtual memory manager, interrupt controller/PIC/APIC, scheduler, drivers, filesystem or SMP. External interrupts remain disabled.

06
PRE-BUILD HEALTH5 MIN

Run the toolchain health check

Open Settings → Toolchain and run the local scan. Ensure that assembler, both cross-compilers, linker, GRUB and xorriso are available. The QEMU executable is needed for the next stage. Confirm that both compiler targets report an x86_64 triple.

Do not skip this

A compiler found on PATH is not necessarily configured for the right target. Kerno checks compiler target triples before compiling.

07
BOOTABLE IMAGE5–15 MIN

Build and validate the ISO

Kerno's native pipeline is deliberately staged. A successful ISO is accepted only after its kernel and boot image pass independent health checks.

01AssembleNASM → ELF64 objects
02CompileC/C++ → freestanding objects
03LinkELF64 x86_64 kernel
04Verify kernelEntry point + Multiboot2
05Stage ISO root/boot/kernel.elf + grub.cfg
06Packagegrub-mkrescue + xorriso
07Inspect ISOISO9660 + El Torito + file paths
08Register artifactOnly after every required check passes
What an ISO contains

The staging directory places the kernel at /boot/kernel.elf and GRUB's menu at /boot/grub/grub.cfg. The ISO must contain a valid ISO9660 volume descriptor and an El Torito boot catalog for legacy BIOS boot.

08
FIRST BOOT5–10 MIN

Boot the ISO in QEMU and inspect output

After the ISO is verified, start the QEMU guest with the matching x86_64 BIOS profile. Inspect the VGA display and COM1 serial output. A real kernel boot should reach the early kernel entry messages; a QEMU process merely staying open does not prove the kernel executed successfully.

  • QEMU process is running and its display is attached.
  • GRUB loads the kernel without a Multiboot error.
  • Serial output reports that kernel entry was reached.
  • Physical memory map and IDT initialization messages appear when enabled.
When it fails

Use the build health report first. Then inspect QEMU process logs and serial output. A valid ISO can still contain a kernel with a runtime fault, so image validation and successful guest execution are separate checks.
